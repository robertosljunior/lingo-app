# P0 recipe/capability gate diagnostic — #106

Date: 2026-08-09
Base: `main` at `a969e5c69794bc4a49ab862ccd8bd2e603c7fb24`

## Question

The learner-facing 10-session audit observed 117/117 answer-requiring activities as option-select. That output alone cannot distinguish:

1. a capability gate that never opens;
2. a learner/harness state that never satisfies the gate;
3. a production recipe that is eligible but loses scoring/selection;
4. a production recipe that wins selection but is replaced or lost during materialization/rendering.

This slice is diagnostic only. It changes no planner, engine, learner-model, cooldown, diversity, recipe weight, assessment or scramble behavior.

## Mechanical contract

`recipe-gate-diagnostic.js` exposes:

- the exact capability-gate predicates with `actual`, `required`, and `met` values;
- pre-scoring recipe eligibility split into domain, runtime, capability gate, licensed-realization contract and presentation-only restrictions;
- selected recipe -> materialized ActivityPlan recipe -> renderer recipe consistency;
- response-contract validity for the materialized recipe, including ordered-token requirements for word order;
- a static audit of the generic learner E2E recognition-answer strategy.

Synthetic learner states are not manually shaped objects. Tests construct valid LearnerEvidenceV2 and run them through `aggregateProfileEvidence()`, so the same aggregation fields/rollups read by runtime gates are populated.

## Locked distinctions

- Curated authored exemplars are not licensed tier-1 merely because V2.24 supports tier-1 licensed realizations.
- Curated `but` examples with authored context can remain eligible for context-dependent recipes when other gates allow.
- Licensed tier-1 material remains ineligible for context-required recipes while retaining `word_order_reconstruction` eligibility.
- Pronunciation runtime unavailability is reported separately and cannot be used as evidence for or against word-order reachability.
- The only approved post-selection recipe substitution currently recognized by this diagnostic is the explicit `meaning_recognition -> context_recognition` presentation variant; any other selected/materialized/renderer divergence is a fallback defect.

## Harness confounder

The generic `answerLearnerActivity()` helper used by the learner-facing diagnostic path answers recognition by clicking the first rendered option. It does not resolve or select the correct option id. Therefore a long run driven by that helper is not a controlled successful-mastery trajectory and cannot by itself prove that a mastery-gated production rung is unreachable.

## Acceptance

The P0 is resolved only when tests prove all of the following mechanically:

- low mastery exposes the failed predicate and the real threshold values;
- valid recognition mastery opens the controlled-production capability predicate;
- the Study Planner can generate a controlled-production/writing focus for a genuinely advanced target;
- `word_order_reconstruction` is eligible before scoring when content/runtime contracts allow it;
- the Lesson Engine can materialize it into an ordered-token ActivityPlan;
- the learner renderer dispatches that same recipe without option-select fallback;
- licensed tier-1 and curated authored context contracts remain distinct;
- the previous UI harness limitation is recorded rather than interpreted as a gate failure.
